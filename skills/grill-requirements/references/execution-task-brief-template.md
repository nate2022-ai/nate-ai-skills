# 显式执行任务书模式 · 独立模板

只在用户明确要求为 AI agent 编写执行任务书、brief、目标任务书或 goal 提示词时使用。任务书是供用户审阅和另行授权的文本候选，不是实施授权；生成阶段不得创建正式主任务或 Goal，也不得执行其中动作。交付后按 `SKILL.md` 的固定三项选择分流。

## 生成规则

- 只写一个能独立闭合的目标。默认控制在 4000 字符以内，作为复制和审阅的兼容预算，不宣称为平台硬上限。
- 用大白话写清真实结果、优先级、边界、证据和止损；删除调研过程、背景故事和执行者打开项目即可看到的普通事实。
- 将结论标为 `已确认事实`、`用户决策`、`AI 默认`、`待验证项` 或 `停车闸`；不得把 AI 默认写成用户确认。
- 已实测的数字、路径和命令必须附来源或日期。无法在当前环境亲自验证的内容写入“任务 0”，标明 `待验证`，不得冒充实测。
- 明确区分硬约束与建议：`只允许 / 不得 / 必须` 违反即不合格；`建议` 允许执行者采用更好方案，但要记录理由。
- 只用允许修改白名单约束写入范围。验收脚本、测试、阈值、基线文件和真相源默认冻结；确需修改时必须已在白名单和授权中明确列出。
- 不可逆动作、真实外部写入、发送、动钱、权限、安装、长期自动化、删除、提交、推送、发布和生产切换必须有单独授权闸。
- 不要求执行者在没有授权的位置新增 `PROGRESS.md` 或 `BLOCKED.md`。优先使用项目现有进度机制；没有现有机制时，只在白名单明确允许的路径记录，或改为在最终回执中报告。
- 只有用户明确同意多 agent 并行时才拆分；每份任务书都必须显式写出同一个整体目标，并分别写清互斥白名单、共享写入唯一负责人和接缝验收。
- 以 `CANDIDATE / NOT_AUTHORIZED` 收尾，不附自动执行命令。
- 生成阶段正式主任务和 Goal 创建数均为 0；任务书内只规定执行者回执，不替原需求对话创建或验收任务。

## 先分型

### 执行型

目标是产生代码、文件、配置或其他可观察变化。每项任务都要有验收命令或明确人工复核证据，并冻结判卷标准。

### 探索型

目标是得到调研、选型、可行性或停止建议。不要用凑数的硬指标逼出虚假确定性；改用：

- 有上限的学习目标和时间/来源预算；
- 每条结论的来源、日期或可复跑步骤；
- 尚未排除的解释和证据缺口；
- 不得强制选出胜者或暂定领先者；证据不足时可以明确“当前无可负责推荐”；
- 不得把 4–8 个来源、最多 5 条结论或任何固定数量写成硬性完成条件；数量只服从最小充分证据；
- “带证据证明此路不通”也可算合格结果。

## 输出结构

按以下顺序生成一个代码块中的完整任务书。方括号内容必须替换，不保留空占位；不适用项写“不适用及原因”。

```text
[任务标题：直接描述要得到的结果]

你是执行者。本任务书是本次工作的范围与验收依据；先核前提，再实施。任务外发现只记录，不顺手修改。

为什么做
[业务意图、完成后世界发生什么变化；1–2 句]

取舍顺序
[冲突时的优先级，例如：准确和可恢复 > 范围完整 > 速度]

已确认与默认
- 已确认事实：[事实｜来源/日期]
- 用户决策：[决定｜影响]
- AI 默认：[默认｜理由｜猜错代价]
- 待验证项：[事项｜最晚验证点]

允许地界
- 工作目录：[绝对路径或明确对象]
- 只允许修改：[逐项白名单；新增文件也逐项列出]
- 只读依赖：[允许读取但不得改的路径/系统]
- 冻结判卷：[测试、验收脚本、阈值、基线、schema 或真相源]
- 明确不做：[外部写入、删除、提交、发布等禁区]

任务 0：前提与基线
1. 运行：[已验证命令，或标“待验证命令”]
2. 预期：[机器可判结果和基线数字]
3. 不符时：[停车条件；写到哪个已授权位置，或最终回执如何报告]
4. 核对通过后：[记录目标、顺序、最大风险；不得扩大白名单]

任务 1：[可独立验收的结果]
- 动作：[最少必要动作]
- 硬约束：[违反即失败的条件及后果]
- 验收：[命令/人工复核｜明确预期｜证据保存方式]
- 反向验证：[故意制造一次受控失败、证明检查会报警、还原后再通过；不适用则说明原因]

[按依赖继续任务 2、任务 3；不要按文件数量机械拆分]

守约与防作弊
- 不得跳过、删除或弱化测试；不得放宽断言、阈值或验收脚本；不得用 mock 替换被测核心；不得用忽略失败的写法制造假绿。
- 测试数、覆盖率或其他基线只允许保持或提高；不适用时写明对应守约指标。
- 不新增未授权依赖、流程、权限、入口或兼容双轨。
- 同一验收连续失败 3 次，停止在该路径上硬试，改做不受影响项或触发停车闸。
- 结果比基线差时，使用已确认的可恢复方式撤回本次变化并如实报告；没有安全恢复方式时不得开始该动作。

停车闸
- [触发条件] → [立即停止的动作] → [仍可继续的只读/不受影响部分] → [需要谁另行授权]

完成条件
1. 结果指标：[机器可判或人工复核的真实结果，不是工作量]
2. 守约指标：[白名单外零变化、冻结判卷未改、外部写入为零等]
3. 证据：[逐项列实际命令输出/文件/截图/哈希；只说“完成”不算]
4. 遗留：[待验证、停车项、已知限制和建议下一步]
5. 止损：[最多轮次/时间预算；到点即停并如实交卷]

结构化执行回执包
1. 实际修改及白名单外变化：[逐项文件/对象；白名单外为 0，若不为 0 必须列明并判停车]
2. 实际命令、结果和证据位置：[命令｜退出码/结果｜日志、文件、截图或哈希位置]
3. Goal/普通任务真实运行状态：[普通任务或 Goal｜平台实际返回的真实标识（当前 Goal 与正式任务共用绑定 threadId；若无独立 Goal ID，明确“独立 Goal ID：无”）｜objective｜状态；不适用写原因，不得用文字候选冒充]
4. 未完成项、阻塞和越权请求：[事项｜原因｜需要谁授权；没有则写“无”]
5. 恢复/回滚状态：[未触发｜已恢复及证据｜无法安全恢复并已停车]
6. 遗留风险及建议下一步：[风险｜影响｜最小下一步]

授权状态：CANDIDATE / NOT_AUTHORIZED
```

任务书代码块之后原样展示：

1. 确认执行，并授权适合时在新正式主任务启动 Goal；
2. 确认执行，但只创建普通正式主任务；
3. 暂不执行。

## 防止任务书自相矛盾

交付前逐项检查：

1. 目标、白名单、任务动作和验收是否指向同一个结果；任何动作都能追溯到目标。
2. 是否把尚未验证的命令、数字或环境写成了事实；若是，移入任务 0。
3. 是否要求改变冻结判卷却又禁止改变；若是，拆开授权或重新设计验收。
4. 是否存在“为了通过测试而可以修改测试”的作弊空间；若是，冻结对应文件和指标。
5. 是否有静默失败点；若坏了没人知道，增加反向验证或明确人工复核。
6. 是否把不可逆动作交给无人值守执行；若是，改成停车闸。
7. 是否擅自增加多 agent、提交、推送、发布、安装、外部发送或生产切换；若是，删除并列为待授权。
8. 是否在任务书正文中出现自动执行命令或把候选写成已授权；若是，修正后再交付。
9. 是否漏掉结构化执行回执包，或允许执行者自判终验；若是，补齐回执并把终验责任留在原需求对话。
