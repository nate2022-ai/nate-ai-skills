# 显式执行任务书模式 · 独立模板

识别到任务书请求，或已授权正式任务需要补齐交接时使用。生成与执行授权沿用主入口。先核对以下生成条件，再按已确认需求输出独立任务书。

## 生成规则

- 关键执行边界未定时，不得生成完整任务书，也不用猜测、占位符或 AI 默认补齐。高影响决定已确认或可明确放入后续停车闸时再生成。

- 围绕一个能独立闭合的整体目标，完整保留多个必交结果、优先级、决定及理由、关键约束和验收依据。
- 用大白话写清真实结果、优先级、边界、证据和止损；删除调研过程、背景故事和执行者打开项目即可看到的普通事实。具体方法由执行者选择，保留用户指定或风险必需的步骤。
- 将结论标为 `已确认事实`、`用户决策`、`AI 默认`、`待验证项` 或 `停车闸`；不得把 AI 默认写成用户确认。
- 已实测的数字、路径和命令必须附来源或日期。无法在当前环境亲自验证的内容写入“任务 0”，标明 `待验证`，不得冒充实测。
- 明确区分硬约束与建议：`只允许 / 不得 / 必须` 违反即不合格；`建议` 允许执行者采用更好方案，但要记录理由。
- 按风险用模块、目录或具体对象界定修改白名单，范围内必要的配套文件可自主处理；重要冻结对象精确列出。保留已确认验收标准与关键行为覆盖，开发测试可在授权内新增、重构或合并；明确冻结的独立验收、基线或真相源，变更仍须对应授权。
- 按主入口授权规则，把本任务的允许动作、禁止动作和待授权停车闸写入文本；逐项暴露适用的不可逆、真实写入、外部发送、费用、权限、安装、自动化、删除、提交和发布边界。
- 不要求执行者在没有授权的位置新增 `PROGRESS.md` 或 `BLOCKED.md`。优先使用项目现有进度机制；没有现有机制时，只在白名单明确允许的路径记录，或改为在最终回执中报告。
- 长任务按入口选定的接续规则填入下方具体任务依据、进度位置、恢复与变更要求，使执行者无需继承生成者的聊天也能接续。
- 获准拆分时，每份任务书都必须显式写出同一个整体目标，并分别写清修改地界、依赖、接口与接缝验收；只交付该分工必需的完整输入。分工授权沿用主入口，协作要求使用入口选定的规则。
- 任务书规定执行者回执与实际验收责任方；需要独立验收时按风险和证据缺口选择抽查，必要时由验收方保留未公开样例，不增加未告知的验收要求。

## 先分型

### 执行型

目标是产生代码、文件、配置或其他可观察变化。每项任务都要有验收命令或明确人工复核证据，并冻结判卷标准。

### 探索型

目标是得到调研、选型、可行性或停止建议。不要用凑数的硬指标逼出虚假确定性；改用：

- 有上限的学习目标和时间/来源预算；
- 每条结论的来源、日期或可复跑步骤；
- 尚未排除的解释和证据缺口；
- 不得强制选出胜者或暂定领先者；证据不足时可以明确“当前无可负责推荐”；
- 来源和结论的数量服从最小充分证据；
- “带证据证明此路不通”也可算合格结果。

## 输出结构

授权状态按主入口如实填写：未授权候选用 `CANDIDATE / NOT_AUTHORIZED`，已授权交接写已有用户决定与具体范围。以下字段必须填成本任务的完整执行依据，不能仅链接生成者的聊天或 Skill。

以下结构按需选用和合并，在一个代码块中交付任务书。不保留空占位；目标、授权边界和验收要求不得因精简遗漏。默认简短收口不限制用户明确请求的完整任务书，不设默认字数。

```text
[任务标题：直接描述要得到的结果]

你是执行者。本任务书是本次工作的范围与验收依据；先核前提，再实施。任务外发现只记录，不顺手修改。

为什么做
[业务意图、完成后发生什么变化]

取舍顺序
[冲突时的优先级及已确认理由]

已确认与默认
- 已确认事实：[事实｜来源/日期]
- 用户决策：[决定｜理由与来源｜影响]
- AI 默认：[默认｜理由｜猜错代价]
- 待验证项：[事项｜最晚验证点]

允许地界
- 工作目录：[绝对路径或明确对象]
- 只允许修改：[已授权模块、目录或对象；范围内必要配套文件可自主处理，重要冻结对象精确列出]
- 只读依赖：[允许读取但不得改的路径/系统]
- 冻结判卷：[已确认验收标准及明确冻结的独立验收、基线、schema 或真相源；区分可正常维护的开发测试]
- 明确不做：[外部写入、删除、提交、发布等禁区]

任务 0：前提与基线
1. 核对：[有效任务依据、全部必交结果、已有进度与实际现场；已读且未变的内容复用]
2. 运行：[已验证命令，或标“待验证命令”]
3. 预期：[机器可判结果和基线数字]
4. 不符时：[停车条件；写到哪个已授权位置，或最终回执如何报告]
5. 核对通过后：[记录目标、顺序、最大风险；不得扩大白名单]

任务 1：[可独立验收的结果]
- 动作：[最少必要动作]
- 硬约束：[违反即失败的条件及后果]
- 验收：[命令/人工复核｜明确预期｜证据保存方式]
- 反向验证：[故意制造一次受控失败、证明检查会报警、还原后再通过；不适用则说明原因]

[按依赖继续任务 2、任务 3；不要按文件数量机械拆分]

长任务接续（预计跨多轮、多阶段或跨上下文时填写）
- 固定依据：[目标、范围、不做事项、已确认决定及理由、AI默认、验收和未决条件的版本/来源]
- 唯一进度位置：[所属项目现有状态/推进机制及已授权路径；不另建第二套主进度]
- 阶段记录：[对应必交结果、实际完成与证据、对其他结果/关键约束/已有成果的影响与必要验证、剩余工作、阻塞和接续点；不堆逐操作日志]
- 恢复顺序：读进度 → 核对实际文件与结果 → 对照固定依据 → 继续未完成项。不凭聊天摘要重规划，不重复已有证据的完成项；差异先核查，不能改记录掩盖。
- 变更边界：实现细节可在授权内调整；目标、范围、关键约束或验收标准变化，先说明影响并由用户决定，实施须有明确授权，不降低标准换取完成。

守约与防作弊
- 不得降低验收标准、掩盖失败或用 mock 替换本应验证的核心来制造通过；明确冻结对象按授权维护。
- 开发测试可在授权内新增、重构、合并或清理失效项，保持关键行为覆盖；不以测试数量或覆盖率单一指标代替有效验证。
- 不新增未授权依赖、流程、权限、入口或兼容双轨。
- 无新证据或有效进展的重复失败应停止该路径并改方法；有明确新证据且预期收益仍合理时可继续，遵守用户本次明确的次数、时间与费用上限。
- 出现影响目标或关键约束的退化时，停止扩散，按已确认的恢复方式处置并如实报告；需恢复保障的动作应先具备可行的恢复方法。

停车闸
- [触发条件] → [立即停止的动作] → [仍可继续的只读/不受影响部分] → [需要谁另行授权]
- 规则冲突处理：[按主入口规则写明本任务受影响动作、可分离工作、无法分离时的暂停范围及裁决后接续条件]

完成条件
1. 结果指标：[全部有效必交结果及适用的共同使用结果，逐项对应证据；未完成、待验收、获批取消或延后分别说明，不混记为完成]
2. 守约指标：[白名单外零变化、冻结判卷未改、外部写入为零等]
3. 证据：[逐项列实际命令输出/文件/截图/哈希；只说“完成”不算]
4. 遗留：[待验证、停车项、已知限制和建议下一步]
5. 止损：[无新证据或有效进展时改方法；用户本次明确的成本/次数/时间上限及到限处理]

结构化执行回执包
1. 实际修改及白名单外变化：[逐项文件/对象；白名单外为 0，若不为 0 必须列明并判停车]
2. 实际命令、结果和证据位置：[命令｜退出码/结果｜日志、文件、截图或哈希位置]
3. Goal/普通任务真实运行状态：[普通任务或 Goal｜工具实际返回的任务或 Goal 标识（不预设绑定关系；若无独立 Goal ID，明确“独立 Goal ID：无”）｜objective｜状态；不适用写原因，不得用文字候选冒充]
4. 未完成项、阻塞和越权请求：[事项｜原因｜需要谁授权；没有则写“无”]
5. 恢复/回滚状态：[未触发｜已恢复及证据｜无法安全恢复并已停车]
6. 遗留风险及建议下一步：[风险｜影响｜最小下一步]

授权状态：[按主入口填写实际授权与范围；未授权候选使用 CANDIDATE / NOT_AUTHORIZED]
```

## 防止任务书自相矛盾

交付前逐项检查：

1. 目标、白名单、任务动作和验收是否指向完整结果；任何动作都能追溯到目标，反向核对每项已确认必交结果都有对应阶段、约束和验收。
2. 是否把尚未验证的命令、数字或环境写成了事实；若是，移入任务 0。
3. 是否要求改变冻结判卷却又禁止改变；若是，拆开授权或重新设计验收。
4. 是否降低验收或掩盖失败来制造通过；开发测试正常维护后，关键行为覆盖与明确冻结对象是否仍受保护。
5. 是否有静默失败点；若坏了没人知道，增加反向验证或明确人工复核。
6. 是否把不可逆动作交给无人值守执行；若是，改成停车闸。
7. 是否擅自增加正式执行任务、提交、推送、发布、安装、外部发送或生产切换；若是，删除并列为待授权。内部代理分工不扩大已有授权，同一实际修改范围单一写入者，审查保持独立。
8. 是否在任务书正文中出现自动执行命令或把候选写成已授权；若是，修正后再交付。
9. 是否漏掉结构化执行回执包，或允许执行者自判终验；若是，补齐回执并明确现行总责方的终验责任。
10. 长任务是否携带固定依据、唯一进度位置及授权、阶段证据、恢复检查和变更要求；任务书是否遗漏、曲解或扩展了已确认决定；必要信息缺失时补齐或列前置条件，不以聊天记忆替代。
11. 规则冲突是否按实际影响暂停，无法可靠分离时停整体；已有裁决与授权足够时直接接续，存在真实授权缺口时才补问。
