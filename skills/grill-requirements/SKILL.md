# 需求榨干：研究规划与执行任务书

先识别模式与授权，再做最小事实研究并校准真实目标。目标清楚时直接继续；只有目标、问题定义或当前方向存在高影响不确定时，才展示双向钢人并暂停。随后采用成熟默认，只把真正需要用户拍板的高影响决策逐个问清。默认交付完整规划；只有用户明确索要给执行 agent 使用的任务书时，才交付独立执行任务书。生成阶段的两种产物都只是文本，不自动获得执行授权，也不创建正式主任务或 Goal。

## 双模式路由

先判定模式，再开始研究；不要在流程末尾临时混写两种产物。

### 默认：研究规划模式

用户要求问透需求、先研究再规划、压力测方案、形成设计或消除实施前歧义时，使用本模式。高影响决策收口后，输出最终详细规划和一份简短的未授权候选 Goal。

### 显式：执行任务书模式

只有用户明确要求为另一个 AI agent 写“执行任务书、brief、目标任务书、goal 提示词”，要求“让 agent 独立跑”，或明确要求把任务拆给多个 agent 时，才使用本模式。先完成同样的研究与高影响决策收口，再输出一份独立任务书；不要把“请直接实施”“帮我修复”之类普通执行请求擅自改写成任务书请求。

执行任务书模式的生成阶段不是实施阶段。任务书先供用户审阅；生成完成前不要创建正式主任务、不要调用 Goal 能力，也不要执行任务书中的动作。任务书交付后的明确执行选择按下文“任务书交付后的执行分流与回流”处理。

### `goal` 授权歧义闸

本闸优先于研究、安全默认和业务范围澄清。用户只说“goal”且当前会话与命令状态仍无法判断是在索要未授权任务书，还是已经发出授权执行目标时，只问：“你是要我只生成未授权的候选任务书，还是已经授权我开始执行？”即使用户同时说“本轮不要执行”，这也只限制当前动作，不能替代对 `goal` 授权语义的澄清。不得自行落到只读诊断，不得改问是否写真实数据、允许读取哪个数据源、范围或技术细节；答复前不创建或调用 Goal，不开始实施。

### 路由冲突

- 用户同时要求规划和任务书时，先完成规划，再按已确认规划生成任务书；明确标出两者的关系，避免双份事实互相漂移。
- 用户要求多 agent 并行时，把“是否拆分”视为高影响授权决策；未明确同意就保持单任务。
- 公开需求入口只使用 `grill-requirements`；不要再引导用户寻找其他需求或任务书 Skill 名。

## 不可破坏的原则

- 先研究当前事实、约束、成熟方案、同类实现、主要风险和 MVP 边界，再决定是否需要提问。
- 目标校准是每次调用都要执行的检查，不是每次都要展示和停顿的固定仪式；目标明确时不得机械制造反方或要求用户重复确认。
- 优先采用成熟、安全、可逆、低成本的默认方案，不把可查事实和普通实现选择转嫁给用户。
- 只问同时通过“无法查明、无法安全默认、答案会显著改变结果”三道准入条件的高影响决策；默认一次只问一个，不合并成问卷。
- 每题先给针对性研究结论、推荐答案和简短理由，不把分析成本推给用户。
- 用正文的 `1 / 2 / 3` 选项提问，不使用点选、填框等交互组件。选项要互斥且真实，不制造假选项。
- 按依赖顺序解决决策。上游问题未定时，不急着询问会被它改写的下游细节。
- 直接指出冲突、隐含假设、过度设计和低回报需求；先审问题是否成立，不默认所有想法都应该实现。
- 允许用户回答“不知道”“以后定”或自定义答案。将它们分为必须在实施前解决、可在某阶段再解决、可安全默认三类。
- 展示局部结论、阶段小结或默认方案不等于要求用户逐项确认；只有状态为“需要拍板”的事项才要求回复。
- 以实际后果、逻辑耦合和返工成本判断影响，不按“界面、措辞、技术实现”等类别机械降级。
- 不要展示隐藏思维链。只说用户需要判断的事实、取舍、推荐和理由。
- 在研究和生成阶段，不写代码、不修改业务文件、不操作外部系统、不创建正式主任务、不创建或调用 Goal，也不开始实施规划或任务书。

## 共用工作流程

### 1. 定义访谈对象

用一小段话复述当前理解，只包含：

- 要解决的真实问题；
- 预期最终产物；
- 已知边界与当前不执行的范围；
- 已发现的最大不确定点。

如果连访谈对象都无法确定，先继续研究；仍无法查明且不同答案会显著改变目标或范围时，才把第一题用于确定对象。否则直接进入决策树过滤。

### 2. 先研究再判断

在提问前完成与当前决策有关的最小充分研究：

- 当前对话、项目入口、现行真相源、推进状态和实际文件；
- 已知业务、技术、时间、预算、权限、合规和授权约束；
- 权威来源、成熟方案、同类实现及其适用条件；
- 最可能造成返工、越权、数据错误、不可逆后果或无法验收的风险；
- 能闭合真实目标的最小可行范围（MVP）及明确不做事项。

外部事实的时效性或准确性会影响选择时，先查权威来源。研究的目标是缩小需要用户决策的范围，不是堆积材料或延迟收口。

将获得的信息分为：

- `已确认事实`：可由当前证据直接支持；
- `待验证项`：有根据但未足以确认，可在规划或停车闸中验证；
- `用户决策`：没有唯一事实答案，必须由用户取舍。
- `AI 默认`：已有成熟、安全、可逆、低成本方案，可直接采用并披露。

不要把事实、AI 默认或可延后验证的事项伪装成用户决策。

### 3. 目标校准与双向钢人闸

每次调用都必须执行目标校准检查。先基于已确认事实和明确标注的推断，依次形成：

1. 对用户真正要解决的问题、期望结果和成功含义的最有力重述；
2. 当前方向成立的最强理由、适用条件和潜在收益；
3. 最强反方或替代路径，包括不做、缩小范围、改流程或改用成熟方案；
4. 双方真正的分歧，以及最可能改变目标、路径、范围、优先级、成本、风险或验收标准的关键变量。

执行时遵守：

- 不把 AI 推测的隐藏动机写成事实；明确区分已确认事实、推断、假设和用户价值选择。
- 问题没有天然正反双方时，比较“当前路径”和“最强可行替代路径”；不得为了凑正反双方制造虚假争议，也不得预设反方必然正确。
- 目标、问题定义和当前方向已经清楚，且不存在会使方案改道的高影响不确定时，把校准后的真实目标和关键变量记入决策账本，不单独展示目标校准卡，不要求用户重复确认，直接继续建立决策树。
- 只有目标、问题定义或当前方向存在高影响不确定，且该不确定同时通过“无法查明、无法安全默认、答案会显著改变结果”三道准入条件时，才展示下列卡片并暂停：

```text
目标校准卡 · 双向钢人
真实问题：[真正要解决的问题和期望结果]
当前方向的最强论证：[成立理由、适用条件和主要收益]
最强反方或替代路径：[最难回避的反对理由或更强路径]
真正分歧：[双方依赖的不同前提或价值取舍]
关键变量：[最可能改变结论的一个变量]
AI 拟采用方向：[推荐及主要取舍]
状态：需要拍板
```

卡片后只问一个最上游、最可能改变目标或方向的问题，并沿用下文的 `1 / 2 / 3` 选项结构和推荐理由。用户回答前不得进入功能、流程、界面、技术实现或执行任务书细节。收到回答后，先更新真实目标、成功标准和决策账本，再继续后续流程。

`goal` 授权歧义闸始终优先于本节；不得借目标校准绕过授权判断或开始实施。

### 4. 建立并过滤决策树

按任务实际情况选取分支，不强制全部覆盖：

1. 问题是否成立，成功意味着什么；
2. 使用者、利益相关者与决策权；
3. 范围、明确不做事项与优先级；
4. 当前流程、现行真相源与主要断点；
5. 理想主流程、例外、失败与恢复分支；
6. 角色、权限、审批和通知；
7. 数据来源、字段口径、更新方式与质量标准；
8. 产物、界面、报表、文档或对外表达；
9. 依赖、集成、迁移、兼容与回滚；
10. 成本、时间、注意力、安全、合规和其他约束；
11. 阶段划分、停车闸、验收证据与失败兜底；
12. 交付后的所有权、维护、监控和退役。

逐个分支先研究、再尝试安全默认，最后才判断是否需要用户决定。一个问题只有同时满足以下条件才能询问用户：

1. 无法通过当前对话、项目文件、工具、权威来源或成熟方案查明；
2. 无法采用安全、可逆、低成本的成熟默认；
3. 不同答案会明显改变目标、范围、优先级、成本、风险、不可逆动作、授权边界或验收标准。

任一条件不满足，就不提问。不能因为某项属于界面、措辞或技术实现就自动认定为低影响：面向客户的承诺性措辞、影响关键或不可逆操作的界面，以及影响数据完整性、审计、恢复或迁移的技术实现，都可能是高影响决策。

### 5. 按三档处理

#### 高影响且必须由用户决定

先输出针对性研究结论和“局部结论卡”，再提出一个问题。局部结论卡固定使用：

```text
局部结论卡 · [主题]
已确认事实：[与本决策直接相关的事实]
AI 拟采用方案：[推荐选项或建议方向]
理由与可能影响：[主要依据、取舍和受影响结果]
状态：需要拍板
```

随后使用这个结构：

```text
问题 N · [决策主题]

[一句话说明这个决策会影响什么]

1. [选项一]（推荐）
2. [选项二]
3. [选项三]

我推荐 1：[简短理由和主要取舍]。

请回复 1 / 2 / 3，也可以直接说你的答案。
```

根据问题使用 2–3 个真实选项；必要时可以不列选项，但仍要给推荐答案。不要在同一轮夹带第二个需要拍板的问题。

#### 有逻辑关联但可以安全默认

输出局部结论卡，状态写为“默认继续”，记入决策账本后继续，不要求用户回复：

```text
局部结论卡 · [主题]
已确认事实：[与默认方案直接相关的事实]
AI 拟采用方案：[成熟默认]
理由与可能影响：[为何安全、可逆、低成本，以及可能影响]
状态：默认继续
```

#### 纯低影响细节

不打断访谈，不逐项展示。直接记入默认决策账本，在阶段小结或最终规划中集中披露；如果后续证据表明它会造成高影响后果，再重新分级。

### 6. 执行高影响决策循环

收到回答后：

1. 用一句话确认刚得到的决策；
2. 更新对用户真实问题、核心动机、最终目标、成功标准、范围和关键约束的整体理解；
3. 将决策、理由、影响和状态记入当前决策账本；
4. 检查新回答是否推翻旧假设、产生新分支或与旧答案冲突；
5. 优先处理最可能改变上述理解、导致方案改道或显著降低理解不确定性的下一个分支；
6. 记录自上次重新评估以来已完成的高影响决策数。

每完成 3 个高影响决策，必须先输出阶段小结并重新检查决策树。阶段小结至少区分：已确认事实、用户决策、AI 默认、待验证项、停车闸，以及仍可能使方案改道的分支。

重新评估后如果仍要继续问，在下一个问题前明确说明：

- 为什么该问题无法继续研究或采用安全默认；
- 不回答会使哪个重要结果发生变化。

如果剩余事项不会让方案根本改道，就停止追问：采用成熟默认、列为待验证项，或放入后续停车闸。三题机制是强制重新评估的软预算，不是总计三题的硬上限；不到三题但已经满足收口条件时也立即停止。

### 7. 关闭决策树

只在同时满足以下条件时建议结束访谈：

- 高影响分支已经确定或明确延后到某个停车闸；
- 目标、范围、不做事项和优先级没有重大矛盾；
- 会改变方案的主流程、关键异常和失败兜底已被覆盖；
- 高影响的依赖、风险、权限、真实写入、数据口径和不可逆动作确认闸已经暴露；
- 有可观察的完成标准和验收证据；
- AI 对用户真实问题、核心动机、最终目标、成功标准、范围和关键约束的整体理解，自评达到至少 95%；
- 对真实需求和目标不存在已知的高影响歧义；
- 剩余未决项不会让当前规划根本改道。

`95%` 只指对用户真实目标和高影响决策的整体理解，不要求掌握所有界面、措辞和普通实现细节，也不要求把自评伪装成可精确计算的数学概率。界面、措辞或技术实现一旦会影响客户承诺、关键操作、数据完整性、风险、授权或验收，仍按实际后果提升为高影响问题。

满足条件后输出“共同理解摘要”，只列目标、范围、关键用户决策、AI 默认、待验证项、停车闸和验收口径，然后进入已选模式的交付。摘要是可纠正的阶段结论，不要求用户逐项确认；只有出现新的高影响冲突时才恢复提问。

### 8. 按模式生成交付物

#### 研究规划模式

高影响决策已确认或进入明确停车闸后，完整读取 [references/final-plan-template.md](references/final-plan-template.md)，并按它生成最终规划。模板章节是 AI 的输出责任，不是要求用户逐项回答的访谈清单。

规划必须：

- 完整保留已确认的决策和理由；
- 明确区分已确认事实、用户决策、AI 默认、待验证项和停车闸；
- 保持完整、可追溯且没有隐藏的高影响分支，不用重复、堆字或虚构细节填满模板；
- 让每个阶段都有输入、动作、产物、停车闸和验收证据；
- 对不适用的类别标明“不适用及原因”，不用想象出来的需求填空；
- 生成单独的文本“候选 Goal”，至少包含目标结果、交付物、包含范围、排除范围、验收证据、前置条件和未决闸门；
- 最终可见输出必须出现精确字面量 `CANDIDATE / NOT_AUTHORIZED`；不要只用“候选”“未授权”等近义改写替代；
- 以一个单独的“执行授权状态”收尾，明确规划完成不等于获得实施授权；
- 不调用或创建 Goal，不写代码，不操作外部系统，也不开始实施规划。
- 规划产物不得直接实施；用户随后要求执行规划时，先派生一份独立执行任务书，再按任务书交付后的固定选择处理。

#### 执行任务书模式

高影响决策已确认或进入明确停车闸后，完整读取 [references/execution-task-brief-template.md](references/execution-task-brief-template.md)，并按它生成一份独立任务书。生成前必须确认：

- 真实目标、任务类型、允许修改白名单和明确禁区已经清楚；
- 基线事实有来源和日期，无法亲自验证的命令或数字已放入“任务 0”，没有伪装成实测；
- 每个阶段都有机器可判或人工可复核的验收证据，判卷标准不会被执行者自行修改；
- 不可逆动作、真实写入、外部发送、权限、安装、自动化、删除、提交和发布都有独立授权闸；
- 高风险授权未决时只输出局部结论卡，再问恰好一个最上游授权问题；退款金额、审批人、可操作店铺、失败恢复等关键边界未定时，不得生成完整任务书，也不得用占位符或 AI 默认补齐；
- 任务规模能在一个目标内闭合；需要拆给多个 agent 时已获得用户明确同意，且写清互斥地界和接缝责任。

任务书必须：

- 保留目标意图、优先级、用户决策、AI 默认、待验证项和停车闸，不把默认冒充用户确认；
- 使用白名单约束允许修改路径，冻结验收脚本、测试、阈值和基线，点名最可能的作弊达标方式；
- 把未验证命令、环境和数字放入任务 0，要求先核对再动工；
- 只在白名单允许的位置记录进度和阻塞，不擅自在项目根新增 `PROGRESS.md` 或 `BLOCKED.md`；
- 对静默失败设置反向验证，对连续失败、结果退化和越权请求设置止损；
- 默认控制在 4000 字符以内，作为便于复制和审阅的兼容预算，不把它宣称为当前平台硬上限；压不下时先缩小范围，只有用户明确同意才拆分；
- 以 `CANDIDATE / NOT_AUTHORIZED` 收尾，不附自动执行命令；生成阶段不创建正式主任务、不调用或创建 Goal，也不实施任务书。

如任务书需要独立验收，可在当前会话侧保留 1–3 个不写入任务书的抽查点；执行者自报完成不能替代复核。

## 任务书交付后的执行分流与回流

### 1. 先交付文本，再展示固定选择

任务书完整交付前保持零执行副作用：生成阶段正式主任务创建数为 0，Goal 创建数为 0。交付 `CANDIDATE / NOT_AUTHORIZED` 任务书后，原样展示且只展示以下三项执行选择：

1. 确认执行，并授权适合时在新正式主任务启动 Goal；
2. 确认执行，但只创建普通正式主任务；
3. 暂不执行。

只有明确选择 1 才获得“可以评估 Goal 是否适合”的授权；这仍不是强制创建 Goal。明确选择 2 时只创建普通正式主任务。普通“开始”或“执行”只表示执行确认，不得推断为选择 1；在任务书已完整交付且没有其他授权歧义时，安全采用普通正式主任务。选择 3、没有执行确认或出现新的高风险授权缺口时，不创建任务并停车。

### 2. 创建真正的同级正式主任务

获得执行确认后，使用当前 Codex 正式 task/thread 能力创建一个用户可见、可重新进入、与原需求对话同级的新任务。禁止使用 fork、subagent 或内部协作代理冒充正式主任务，也不要另建临时验证任务或第二个执行任务。

- 有项目归属时，先读取正式项目列表并绑定正确项目；无项目归属时才使用 projectless。
- 按项目状态选择 Local 或 Worktree，并向用户披露选择理由。Git 项目通常优先 Worktree；用户明确要求当前检出、任务依赖未提交现场或 Worktree 无法保持所需基线时，选择 Local，但先确认没有其他写入者。
- 创建完成后记录真实 `threadId` 和 `hostId`，并从正式任务列表核对它可发现、可重新进入。若 Worktree 仍只返回 `clientThreadId`，等待物化为真实 `threadId` 后再执行后续读取或等待。

新任务必须收到最终任务书、用户本次授权、项目与环境选择、允许修改白名单、禁区、验收命令和结构化回执格式；原需求对话自留的隐藏抽查不得泄漏给执行者。

### 3. 判断 Goal 是否适合并执行安全降级

只有选择 1 且以下条件全部成立，才判定适合 Goal：稳定目标、多步骤、可在授权范围内自治、明确完成标准、所有实施与高风险闸门关闭。

出现任一情况就不适合：一次性或很短的动作、仅规划或研究、频繁需要用户决策、高风险动作未授权、平台能力未经验证、不能独立闭合。此时自动降级为一个普通正式主任务，简要说明具体理由，不再让用户在 Goal、普通任务、fork 或 subagent 之间做技术选择。

`GOAL_FORWARD_STATUS: READY`

正式前向已通过：F08 与 C02 已由原需求对话真实跑通并独立复验。只有明确选择 1 且任务适合时才启用 Goal 路径；后续若平台能力、正式任务可发现性、结果回流或独立验收出现回归，立即关闭该路径并安全降级为普通正式主任务，不得用静态检查、候选文字或执行者自报掩盖回归。

Goal 路径仍须先创建正式主任务，再在新正式主任务内部调用真实 Goal 能力并立即读取真实状态；回执至少记录平台实际返回的真实标识（当前为与正式任务共用的绑定 `threadId`）、objective 和状态。若工具没有返回独立 Goal ID，必须如实写“独立 Goal ID：无”，不得编造。原需求对话的 Goal 创建数必须为 0；仅出现“Goal”或命令文字不算真实运行证据。

### 4. 原需求对话负责回流与终验

原需求对话使用正式任务的等待并读取能力跟进 `threadId` 与 `hostId`，直到新任务完成或需要关注；若执行者提出新增授权、越过白名单或触发停车闸，立即停给用户，不代替用户批准。

任务返回后，原需求对话亲自复跑任务书中的公开验收，并执行 1–3 个执行者不可见的抽查点。执行者自报成功、自己的测试绿灯或结构化回执都不是终验；公开验收或任一隐藏抽查失败，原需求对话必须判失败。

最终只给最多 5 行人话报告，依次说明：通过与否、实际完成、关键证据、遗留问题、下一步。原需求对话负责正式判定，执行者不得自判终验通过。

## 与其他 Skill 的边界

- 本 Skill 是公开的需求研究、规划和执行任务书统一入口；任务书能力已内建，不再分流到另一个公开入口。
- `/提示词增强` 负责整理用户已经表达出来的需求，不负责长时问答挖掘未表达需求。
- 实施、落盘、发布或写入外部系统属于后续独立任务，仍遵守当前项目授权和硬边界；生成任务书不扩大授权。
